# Steam 公告配图设计

## 目标

Steam 游戏新闻卡片按每条公告选择配图。公告正文含有效图片时显示首张有效公告图；公告缺图、图片下载失败或图片解码失败时显示现有固定游戏图。

公告图保持原始纵横比。原图宽度超过卡片正文宽度时等比缩小到正文宽度；原图宽度较小时保持原始尺寸并水平居中。卡片高度随图片实际高度增长，渲染过程不裁剪、不拉伸、不补边。

## 数据来源

新闻主来源继续使用 `ISteamNews/GetNewsForApp/v2`。图片候选按正文顺序解析以下形式：

1. 完整的 Steam 官方 HTTP 或 HTTPS 图片地址。
2. `{STEAM_CLAN_IMAGE}/<clanid>/<file>`。
3. `{STEAM_CLAN_LOC_IMAGE}/<clanid>/<file>`。

`STEAM_CLAN_IMAGE` 转换为 Steam clan CDN 的基础图片地址。`STEAM_CLAN_LOC_IMAGE` 先生成与当前 Steam 语言对应的本地化图片地址，再生成基础图片地址作为同一逻辑图片的备用地址。

RSS 继续作为新闻 API 为空时的备用来源。解析 RSS `<description>` 时先保存 `<img src>`，再将 HTML 转为纯文本；如果条目提供 `<enclosure url>`，该地址排在正文图片之后作为候选。

Community 公告详情页不加入常规抓取过程，避免依赖网页内部数据结构。

## 图片候选与选择

每条 `NewsItem` 的 `image_url` 保存首个规范化图片候选地址，用于 LLM 摘要模式保留图片信息。候选生成函数同时读取 `image_url` 和 `contents`，按首次出现顺序去重。

同一条公告的候选依次尝试。下载、域名校验、内容类型校验、字节限制、像素限制和图片解码全部通过后，该图片成为此公告的配图，后续候选停止请求。不同公告之间可以继续使用现有并发限制。

第三方域名继续使用现有许可规则。第三方图片被拒绝后尝试下一候选；全部候选失败后使用固定游戏图。

## 卡片渲染

游戏新闻按公告逐条处理：

1. 存在有效公告图时，在该公告正文之后显示公告图。
2. 缺少有效公告图时，在同一位置显示对应 AppID 的固定游戏图。
3. 同一游戏含多条缺图公告时，固定游戏图可以重复出现。
4. 游戏分区末尾不再额外追加固定游戏图。

公告图最大宽度等于正文区域宽度，当前卡片为 `900 - 52 × 2 = 796px`。缩放规则如下：

```text
原图宽度 > 796px：目标宽度 = 796px
原图宽度 ≤ 796px：目标宽度 = 原图宽度
目标高度 = 原图高度 × 目标宽度 ÷ 原图宽度
```

公告图没有独立高度上限。现有下载字节上限和解码像素上限继续限制输入图片。固定游戏图继续使用现有 `image_max_height` 配置执行等比缩放。

图片块增加水平对齐属性。公告图和逐公告固定图使用居中对齐；其他卡片类型保持现有布局。

## LLM 摘要模式

LLM 处理前从原始公告提取首个规范化图片候选地址，并在生成摘要 `NewsItem` 时保留到 `image_url`。摘要文本可以删除图片标记，图片选择仍依据保留的引用完成。

## 失败处理

图片地址格式无效、域名未获许可、请求失败、响应并非图片、文件超过字节限制、图片超过像素限制或解码失败，均视为当前候选失败。失败冷却和缓存继续使用现有实现。

固定游戏图也获取失败时，该公告仅显示文字内容。图片问题不影响其他公告和其他推送目标。

## 测试范围

自动测试覆盖以下行为：

1. 完整 URL、`STEAM_CLAN_IMAGE` 和 `STEAM_CLAN_LOC_IMAGE` 的候选顺序与去重。
2. RSS 在正文清理前保留首张图片。
3. 第一候选失败后采用下一有效候选，成功后停止请求。
4. 每条公告分别使用公告图或固定游戏图。
5. 宽图等比缩小，小图保持尺寸，纵向图完整保留。
6. 图片水平居中，卡片高度计入缩放后的完整图片高度。
7. 创意工坊、限时免费、UMO 推送和既有文本模式保持现有行为。

## 上游提交范围

功能分支以 `origin/master` 的 `b2a13cd` 为基点。提交仅包含 Steam 公告图片获取、选择、渲染及相关测试和文档，不包含本地维护分支中的线上专有功能。
